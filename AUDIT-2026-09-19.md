## 1. macOS clipboard echo loop

### Symptom
Copying files in Finder sent their names to the other devices (expected and
wanted). But pasting back on the Mac afterwards produced the *text* that had
been sent, instead of the files. Content also bounced repeatedly between
devices.

### Evidence
Captured live in `~/.clipsync/clipsync.log` before the fix:

```
19:12:11 [INFO] Sent:     this pop up keep poping up when i try to...
19:12:11 [INFO] Received: this pop up keep poping up when i try to...
19:12:11 [INFO] Sent:     this pop up keep poping up when i try to...
19:12:11 [INFO] Received: this pop up keep poping up when i try to...
19:12:12 [INFO] Received: this pop up keep poping up when i try to...
```

Five hops in a single second for one copy.

### Root cause
Not the relay. Both `server-standalone/main.py` and `desktop-client/host_server.py`
correctly skip the sender when broadcasting (`if connection is sender: continue`).

It was a time-of-check/time-of-use race inside `desktop-client/app.py` between
two threads:

- `_receive_loop` did `self.last_clipboard = content` **and then**
  `set_clipboard(content)`.
- `_poll_clipboard` ran independently every 0.5 s.

Between those two statements the guard variable already held the *new* value
while the OS clipboard still held the *old* one. A poll landing in that window
compared old-vs-new, concluded the user had copied something fresh, and
broadcast the stale content. The receiving device then applied it, hit the same
race, and sent it back.

The window is the duration of the clipboard write:

| Platform | Write path | Typical duration |
|---|---|---|
| Windows | in-process Win32 `SetClipboardData` | microseconds |
| macOS | `pbcopy` subprocess | tens of milliseconds |

Three orders of magnitude. That is the entire reason this only ever showed up on
the Mac.

Compounding it: `set_clipboard` writes plain text, which **replaces the whole
pasteboard**. Any echo arriving after a Finder file copy destroyed the file
references, so Cmd+V pasted file *names* instead of files.

### Fix (`desktop-client/app.py`, `desktop-client/clipboard.py`)
1. **Echo-suppression table.** `_recent_sync_values`, an `OrderedDict` with a 15 s
   TTL and a 32-entry cap, records every payload that crosses the wire in either
   direction. The poller consults it before broadcasting and silently adopts a
   known value instead of re-sending it.
2. **Poller parking.** `_applying_remote` plus `_clip_lock` hold the poller still
   while a remote write lands, closing the race window entirely.
3. **Read-back verification.** After writing, the clipboard is read back and
   `last_clipboard` is set to what the OS *actually stored*, not to what we
   assumed. Pasteboards normalise line endings; trusting the assumed value would
   have re-opened the same bug by another route.
4. **File-reference protection.** `clipboard_has_files()` detects a live
   Finder/Explorer file copy. If the incoming text is identical to the text
   flavour already on the pasteboard, the write is skipped so the file references
   survive.
5. **Non-blocking receive.** The clipboard write moved to `asyncio.to_thread` so
   a slow pasteboard no longer stalls the websocket loop.

### Secondary fixes in the same area
- **macOS now uses `NSPasteboard` via PyObjC** instead of `pbpaste`/`pbcopy`.
  `pbpaste` was read with `text=True`, which decodes using the locale encoding.
  Under `launchd`, `LANG` is frequently unset, so accented characters raised
  `UnicodeDecodeError`, were swallowed by the bare `except`, and came back as an
  empty string. For French text this meant silent, intermittent sync failure.
  The `pbpaste`/`pbcopy` fallback remains for environments without PyObjC, but
  now decodes UTF-8 explicitly.
- **Polling is cheaper.** `clipboard_change_token()` wraps `NSPasteboard.changeCount()`
  on macOS and `GetClipboardSequenceNumber()` on Windows. When the counter has
  not moved, the poller does no work at all. Combined with the NSPasteboard
  switch this removes two subprocess spawns per second on macOS — a real battery
  and CPU saving on a laptop.

### Validation
`desktop-client/test_echo_guard.py` — 5 tests against a simulated slow pasteboard:

| Test | Asserts |
|---|---|
| `test_incoming_remote_text_is_never_echoed_back` | receiving triggers no send |
| `test_stale_local_value_is_not_resent_during_the_write_window` | the pre-existing value does not leak out mid-write |
| `test_genuine_local_copy_is_still_sent` | the guard does not swallow real copies |
| `test_same_value_is_not_sent_twice` | no duplicate broadcast inside the TTL |
| `test_file_copy_with_identical_text_is_not_clobbered` | file references survive |

All 5 pass. Critically, **all 5 fail against the previous logic** — the old code
was replayed against the same harness and echoed
`['FINDER: Rapport.pdf, Photo.png', 'hello from iPhone']`, reproducing the
reported symptom exactly.

Run with: `cd desktop-client && python test_echo_guard.py`

## 2. Google sign-in intermittently doing nothing

### Symptom
The Google sign-in button frequently did nothing when clicked. Inconsistent and
hard to reproduce.

### Root cause
`window.google.accounts.id` is a **global singleton**. Calling `initialize()`
replaces the client config and the credential callback for the whole page,
including every button already rendered.

Four components were each calling it, unaware of the others:

| Component | Where | Instances on the homepage |
|---|---|---|
| `AuthModal` (in `Navbar`) | `Navbar.tsx:374` | 1 |
| `AuthModal` (in `PurchaseButton`) | `page.tsx:51`, `page.tsx:200` | 2 |
| `GoogleOneTap` | `layout.tsx:39` | 1 |

Last writer won. Three of those `AuthModal` instances are invisible at any given
moment, but their effects still ran.

Two specific failure modes:

1. **The two-second stomp.** `GoogleOneTap.initOneTap()` awaits a 2000 ms settle
   delay, then calls `initialize()` with the One Tap config. Opening the sign-in
   dialog within two seconds of page load — the completely normal thing to do —
   meant One Tap resumed afterwards and rebound GIS out from under the dialog's
   freshly rendered button. Clicking it then either did nothing or fired the One
   Tap callback, which reloads the page instead of continuing to checkout.
2. **The re-render treadmill.** Parents pass inline arrows
   (`onClose={() => setAuthModalOpen(false)}`), so `handleAuthSuccess` — which is
   in the effect's dependency array — got a new identity on every parent render.
   The effect therefore re-ran constantly, and each run did
   `innerHTML = ""` followed by `renderButton()`. A click landing just after a
   re-render hit a DOM node that no longer existed.

Also found: the `setTimeout(..., 300)` that restored One Tap on close was never
cleaned up, so closing and quickly reopening the dialog fired a re-init into the
wrong mode.

### Fix
**New file `website/src/lib/gis.ts`** — an exclusive lease over the GIS singleton:

- `acquire(ownerId, kind)` where `kind` is `"modal"` (priority 10) or
  `"onetap"` (priority 0). An open dialog outranks passive One Tap, so One Tap
  can never stomp a dialog the user is looking at.
- `initializeFor(ownerId, config)` is a no-op unless that owner still holds the
  lease — the two-second stomp is now structurally impossible.
- `onRelease(cb)` lets One Tap re-arm automatically when a dialog closes,
  replacing the leaked 300 ms timeout.
- `onGisReady(cb)` polls for the script (150 ms, 20 s cap) so opening the dialog
  before GIS has loaded no longer strands the user on the popup fallback
  permanently.

**`website/src/components/AuthModal.tsx`**
- Each instance gets a stable identity from `useId()`, so only the open one
  drives GIS.
- Callbacks moved into refs; effect dependencies reduced to
  `[isOpen, clientId, ownerId]`. The button is no longer redrawn on every parent
  render.
- `renderButton` width is clamped to the container
  (`Math.max(200, Math.min(400, containerWidth))`). The hardcoded `width: 400`
  overflowed the dialog on phones, and the parent has `overflow-hidden`, so part
  of the real hit area was clipped.
- Lease released on cleanup.

**`website/src/components/GoogleOneTap.tsx`**
- An `attemptRef` counter lets a newer call (or an unmount) abandon an in-flight
  attempt mid-await.
- Acquires the lease before initialising, and skips silently if a dialog holds it.
- Re-arms via `onRelease`.
- `window.__reinitOneTap` still exists and still works — nothing that depended on
  it broke.

### What was deliberately NOT changed
- `use_fedcm_for_prompt`, `use_fedcm_for_button`, `itp_support`,
  `prompt_parent_id` — all identical.
- The invisible GIS overlay technique — identical.
- The bottom-right One Tap container — identical.
- The popup fallback for non-FedCM browsers — identical.
- Every sign-in entry point (top-right, bottom-right, Chrome one-click) — all
  still present, visually unchanged.

The fix stops four components racing over one global. It does not change how
signing in works.

## 3. Downloads returning 0 bytes / "nonsense"

### Symptom
Downloads sometimes produced 0 bytes. The macOS installer became undownloadable
after the switch to blob storage, and at least one platform returned a file full
of nonsense.

### Root cause — reproduced exactly
Private Vercel Blobs live on `*.private.blob.vercel-storage.com` and answer an
**unauthenticated** request with `HTTP 403` and the nine-byte body `Forbidden`.

Probed directly during the audit:

```
[url]         status=403 content-type=null content-length=null
              body starts: Forbidden
[downloadUrl] status=403 content-type=null content-length=null
              body starts: Forbidden
```

`CLIPSYNC_MACOS_DOWNLOAD_URL` is set in the Vercel environment, and the route
read it as `process.env.CLIPSYNC_MACOS_DOWNLOAD_URL || "<esiee fallback>"` —
so the env var **overrode the working fallback** — and then did a bare
`NextResponse.redirect()` onto it. The browser followed the redirect, received
403 `Forbidden`, and saved nine bytes as `ClipSync.dmg`.

That single mechanism explains both reported symptoms: nine bytes rounds to
"0 MB", and opening it shows nonsense.

A second, independent contributor: the blob-streaming branch set
`Content-Type` and `Content-Disposition` but **no `Content-Length`**. Browsers
then show an unknown-size download, and some clients report 0 bytes.

### What was verified to be healthy
The ESIEE server was believed dead. **It is not.** All four platforms are live:

| File | Status | Size |
|---|---|---|
| `ClipSync.dmg` | 200 | 31,307,332 B |
| `ClipSync.zip` | 200 | 45,563,270 B |
| `ClypSync.apk` | 200 | 2,918,829 B |
| `ClipSync.ipa` | 200 | 238,286 B |

Artifacts were downloaded and structurally validated:
- **DMG** — valid Apple UDIF image, `koly` trailer present, byte-identical in
  size to the local build.
- **IPA** — valid zip, correct `Payload/ClipSync.app/` layout with the Mach-O
  binary, `Info.plist`, `ShareExtension.appex` and `Assets.car`. 238 KB is
  normal for this app; it is not a broken build.

The blob store also holds all four artifacts at the correct sizes (uploaded
28 Aug 2026). **Neither the builds nor ESIEE were ever at fault.** The route was
trusting a URL it had never checked.

### Fix
**New file `website/src/lib/download-source.ts`** (no Next.js imports, so it is
directly testable):
- `probeUrl()` — validates the URL is absolute http(s), issues a `HEAD` with a
  4 s timeout, rejects any non-2xx, and rejects any body under 1 KB as an error
  page rather than an installer.
- `pickServingSource()` — returns the first candidate that is genuinely serving.

**`website/src/app/api/download/route.ts`** rewritten around a three-tier
resolution, each tier verified before use:

1. **Private Vercel Blob**, streamed through the route so the URL stays
   protected — now with `Content-Length` taken from the blob metadata.
2. **`CLIPSYNC_<OS>_DOWNLOAD_URL`** env override, HEAD-checked first.
3. **ESIEE mirror**, HEAD-checked first.

If every tier is dead the route returns an honest 404 instead of a broken file.

Additional improvements:
- The `CLIPSYNC_*_DOWNLOAD_URL` variables exist in the Vercel environment for all
  four platforms but the code had stopped reading them for anything except
  macOS. All four are wired up now.
- `HEAD` handler added.
- `X-ClipSync-Download-Source` header reports `blob` / `direct-url` / `mirror`,
  and `X-ClipSync-Download-Version` reports the route version — so which source
  served a download can be checked with a single `curl -I` instead of guessed.

### Validation
`website/src/lib/download-source.test.ts` runs against **live endpoints**:

- the real private blob URL is rejected (this was the nonsense download)
- all four ESIEE mirrors confirmed serving
- missing / malformed / non-http / 404 URLs all rejected
- **end-to-end:** with the env var poisoned by the private blob URL, resolution
  falls through to the working mirror
- **end-to-end:** with every source dead, returns null so the route 404s honestly

All checks pass.

## 4. CSRF origin check accepted attacker-controlled hosts

### Root cause
`isSameOrigin()` in `website/src/lib/session.ts` guards `POST /api/auth/session`
and `DELETE /api/auth/session`. It used substring matching:

```ts
originHost.includes("clipsync")
```

Any host merely *containing* that string passed — `clipsync.evil.com`,
`evil-clipsync.net`, `clipsync.attacker.co.uk`. It also fell open on a malformed
origin (`catch { return true }`).

### Fix
Extracted to **`website/src/lib/origin.ts`** with exact-host-or-true-subdomain
matching (`host === allowed || host.endsWith("." + allowed)`), and a malformed
origin now fails closed.

Allow-list: `everything-clipboard.online`, `everything-clipboard.com` (both are
project-owned — the `.com` was briefly and wrongly removed during this audit and
has been restored), `clipsync.vercel.app`, `localhost`, `127.0.0.1`, plus
`*.vercel.app` for preview deployments. Port stripping added so an `Origin`
hostname compares correctly against a `Host` header carrying `:443`.

### Validation
`website/src/lib/origin.test.ts` — 18 checks: 7 legitimate origins allowed,
11 attacker patterns blocked, including every bypass the old code permitted.

## 5. Windows build did not produce its own artifact

### Root cause
`build_windows.bat` produced `build-output/windows/ClipSync/ClipSync.exe` and
stopped. `website/scripts/upload-downloads.mjs` reads
`../desktop-client/build-output/windows/ClipSync.zip` — a file the build never
created. It was being zipped by hand, and at audit time it was **missing from
disk entirely**, so `npm run upload:downloads windows` would have failed with
ENOENT.

### Fix
`build_windows.bat` now:
- refuses to start if `ClipSync.exe` is running, with instructions (it holds a
  lock on the output folder and the old script failed confusingly);
- packages `ClipSync.zip` as part of the build;
- verifies the exe was actually produced before packaging;
- prints exe size, zip size, **embedded version** and build timestamp, so a stale
  artifact is obvious at a glance;
- prints the publish command.

Rebuilt during this audit: **ClipSync.exe 12.39 MB (v1.0.2)**,
**ClipSync.zip 43.76 MB**. Verified running and connected to
`wss://serv.everything-clipboard.com`.

## Open items

1. **`CLIPSYNC_MACOS_DOWNLOAD_URL` in Vercel still holds the stale private blob
   URL.** The route now routes around it automatically, so downloads work either
   way — but the variable should be cleared or repointed. Worth doing for all
   four `CLIPSYNC_*_DOWNLOAD_URL` variables.
2. **The macOS DMG has not been rebuilt** with the v1.0.2 client. That requires a
   Mac; `build_macos.sh` / `build_dmg.sh` must be run there. The currently
   published DMG is still v1.0.1 and **still contains the echo bug** — this is
   the one remaining piece needed to actually close the reported problem for
   Mac users.
3. **The IPA is unsigned**, so it can only be installed by sideloading
   (AltStore, Sideloadly, or Xcode with a free Apple ID, which needs re-signing
   every 7 days). There is no way to install an unsigned IPA on an iPhone or iPad
   without one of those — Apple permits no other route outside the App Store,
   TestFlight, or a paid ad-hoc/enterprise profile. Worth stating on the download
   page so users do not report it as broken.
4. **Not yet audited**: `Navbar.tsx`, `account/page.tsx`, the Stripe webhook,
   `checkout_sessions`, and the Android/iOS clients beyond their echo guards
   (both of which were checked and are correct).
